# Radio programming: SA818-compatible and SR110U are distinct module families

## Why the two paths exist

The contributor tested two physically swapped UHF radio boards:

| Observed module identity | Evidence | Supported path |
|---|---|---|
| SA818S, firmware `V1.2` (`SA818S_V1.2` discovery reply) | Standard channel/tail/volume/filter command ACKs; channel fields separately verified by `DMOREADGROUP` | Existing `sa818` command; standard controls |
| SR110U, firmware `110U-V223` (`+DMOVERQ:110U-V223`) | Legacy channel/volume and selected advanced command ACKs; also matches the previously used SRFRS programmer's README example | Dedicated `sr110u` command; exact V223 gate |

**Both listing titles say SR-FRS, but the tested units report different firmware.**
The purchase-to-unit association is supplied by the owner; the firmware identities
come from the earlier serial tests. A storefront name is not proof of the actual
PCB manufacturer/revision, and an ASIN is not a guarantee of the module fitted
to every production batch. The software therefore uses the connected module's
reply, not the seller title, ASIN, USB IDs or saved settings, to select a profile.
No SA818S-CE suffix or carrier PCB revision has been verified. The USB serial/audio
adapters are not proof of RF module identity. An earlier VHF assumption is not
evidence; this tested SR110U profile is UHF only.

The public [SRFRS README][readme] describes an SR-FRS/SR110U Raspberry Pi HAT
developed with W6IPA for AllStar, Echolink, APRS and digital modes. That is a
source-documented application, not a claim that the contributor's carrier is
that exact design. The public purchase references above identify the owner’s
products; the underlying carrier manufacturer/revision remains unconfirmed.

## User-visible separation and compatibility

**Hardware → Radio programming** displays the detected module name and firmware
on the selected connection. An unidentified reply is not labeled SA818. Unknown
SR110U versions are visibly blocked rather than presented as V223-compatible.
The default-port display follows `/dev/serial0`, then `/dev/ttyUSB0`, like the CLI.
Use **Look for the module** after swapping boards; cached discovery is for display,
not programming authorization. The backend checks identity again for each job;
the SR110U command checks exact firmware again before every write operation.

- SA818-compatible programming continues to use `/usr/bin/sa818`.
- V223 programming uses `/usr/bin/sr110u` from the companion ASL3 update. Its
  fixed protocol cannot be overridden to SA818. Missing/nonexecutable `sr110u`
  stops programming; no fallback to an SA818 write sequence occurs.
- The shared read-only `sa818 version` probe remains for legacy connection
  testing/identity discovery. It sends handshake/version queries, not settings.
  The new entry point shares the packaged implementation to avoid copying protocol code.
- Existing `#/sa818`, `#/hardware/sa818`, API `/sa818`, internal names and
  `/etc/sa818.conf` keys remain compatibility interfaces; they do not identify
  a connected board. New navigation uses `#/hardware/radio`. This is deliberately
  not a bulk rename of SA818-specific manuals, APIs, or settings files.
- Saved settings describe intent, not radio readback. The existing shared file
  contains the last saved profile, not independent per-device storage.
- Modules with no usable version reply retain the existing SA818-compatible
  workflow with an explicit unverified-identity notice. They do not gain SR110U
  advanced controls. A successful handshake alone is not proof of an SA818 model.

Install the matching [ASL3 programmer update](https://github.com/AllStarLink/ASL3/pull/218)
before this frontend/backend revision. Old preview packages providing only
`sa818 --protocol sr110u-v223` do not satisfy the new `sr110u` entry-point dependency.

## Protocol references and evidence matrix

All links below are pinned to public SRFRS commit
`10ac4d00b4802d394baf5a242b09f48fa3618bc7`. The PDFs identify Sunrise Electronics;
the links are a public mirror, **not a newly obtained exact V223 vendor manual**.
PDF page numbers count from the first PDF page.

| Operation | Legacy source | V223 evidence / implemented restriction |
|---|---|---|
| Identity `DMOVERQ` | [V106][v106] §2.2.4, p17; [README][readme] V223 example | Exact `110U-V223` observed; required for writes |
| Group/channel | [V106][v106] §2.2.2, pp16–17; [existing programmer][programmer] | Seven fields; corrected encoder sends RX then TX (see below), RX-tone then TX-tone, two-digit CTCSS; command ACKs are not V223 channel readback |
| Busy lock / companding / power | [V106][v106] §2.2.2, p16 | Bits0/1/2; flags0/5/3/1 ACKed; busy blocking, wattage and companding effects not measured |
| Volume | [V106][v106] §2.2.5, pp17–18 | ACKs at selected levels; UI retains1–8, not the family's documented level9 |
| VOX | [V106][v106] §2.2.6, p18 | Off ACKed; levels1–8 have simulated validation/ordering tests only, never enabled in live verification |
| Mic / timeout | [V106][v106] §2.2.7, pp18–19 | `DMOSETMIC=mic,0,timeout` ACKed; scrambling always off; gain/cutoff timing not measured |
| Power saving | [V106][v106] §2.2.3, p17 | `0` enable / `1` disable ACKed; consumption/wakeup not measured; must be off before VOX-on |

### Why other variants are blocked

[SR110U V303][v303] §2.2.1, p14 lists **RX then TX**, unlike V106 and the existing
V223 programmer. Section2.2.5, p16 has **two MIC fields**; §2.3.5, p23 includes
timeout in `DMOFUN`.

An operator subsequently reported reversed RX/TX operation on V223. The ASL3
encoder correction sends **RX then TX**, consistent with V303 section2.2.1,
instead of copying the older programmer's TX/RX frequency order. Only these two
frequency fields change; tone ordering, flags and legacy MIC/timeout commands
remain unchanged. Simulated serial tests cover positive/negative/zero offsets,
both CLI entry points and unchanged standard SA818 ordering. No new RF test or
V223 channel readback is claimed.

The Hardware form still accepts the intended RX and TX frequencies and passes
RX plus the TX-minus-RX offset. This fix belongs to the ASL3 programmer package;
updating WebUI alone does not change encoding. Existing settings and the radio
are not automatically rewritten. If reversed form values were used as a
workaround, review both intended frequencies before programming again. Do not
automatically swap stored values.

Other firmware, VHF variants, DCS mappings, RSSI/data/reset features and arbitrary
SR-FRS derivatives are not added by this PR. Future support needs its own
identified firmware, sources, serial fixtures and bounded hardware verification.

## Controls and verification limits

V223 exposes channel, CTCSS/none, volume and seven opt-in advanced controls:
busy lock, power, companding, mic sensitivity, transmit timeout, VOX and power
saving. With opt-in off the legacy flags remain busy lock on/high power/
companding off, while the other advanced settings are untouched. Scrambling has
no control; its required MIC field is always0. VOX is off before advanced writes,
and enabled last only if requested with power saving off. Enabling VOX can transmit.

DCS, tail and SA818 pre/de-emphasis/high/low-pass filters are disabled or skipped
and explicitly listed as unapplied. The tested SA818S V1.2 accepted its standard
controls but rejected the probed SR110U advanced commands; those are not offered
as SA818S UART capabilities. No carrier-specific power/sleep GPIO control is added.

ACKs prove command acceptance only. V223 full readback, nonzero VOX, measured
power/mic/companding effects, timeout accuracy, RF direction and power-cycle
persistence remain unverified. Standard SA818S channel readback is separate
prior evidence, not a new generic readback feature in this UI. A failed command
stops later writes but cannot roll back already accepted settings.

Changing/reselecting an existing TX tone does not silently enable RX tone.
Initial selection when both are None retains the existing coupled behavior;
operators may independently set RX to None.

### Discovery after board changes

Discovery normalizes NUL-padded replies like the CLI and reports serial-device
aliases together, so a saved `/dev/ttyAMA0` can match `/dev/serial0` without
changing the saved port. Automatic selection still follows the CLI's port order.
Use **Look again** after swapping a board; it remains available after successful
detection. Cached discovery expires after 30 seconds on the next request, and
connection tests refresh it. Discovery and programming requests in this WebUI
instance are serialized; the write-time firmware check remains authoritative.
This does not coordinate independently launched command-line programmers.
